devkit · runbook 1c · php versions

macOS · ~20 min · phases 0–5
0/0

What you're proving: devkit sees every php@X.Y keg, which one is global, which fpms answer, which sites each serves — and can switch, install and update them. Phase 2 is the acid test of the task runner: valet use restarts the very fpm serving the dashboard, and the task has to outlive it. Precondition: 1b committed.

0Apply and test ~3 min

cd ~/Code && unzip -o devkit-1c.zip -d ~/Code/ && cd devkit && vendor/bin/pest && npx tsc --noEmit && npm run build
Tests: 42 passed — +BrewBridge 3 · PhpManager 3 · Api/Php 5, and Api/Status now pins php.installed
BrewBridge is tested against a fake Homebrew prefix (Cellar, opt symlinks, the tap's Formula dir) — nothing in the suite touches /opt/homebrew.

2Switch the global version from the dashboard the task must survive its own fpm restart~4 min

open http://devkit.test/php
8.4 in gold with "global" · "devkit needs 8.x+" top-right · green dot on rows whose fpm answers · sites column · php.ini paths · "use" only on rows at or above that floor, greyed below it
The floor is read from vendor/composer/platform_check.php — whatever your lock file resolved to. With current Symfony/Pest it is 8.4, so the only other switch target is 8.5. That's the point: switching the global fpm below devkit's own requirement takes the dashboard down (500 from Composer's platform check), which is exactly what happened before this guard read the real number.
8.5 row → use → "switch global to 8.5? the dashboard restarts with it." → yes
→ enqueuing… → running valet use php@8.5… → (nginx restarting) → the poll fails for a few seconds while fpm 8.4 stops and 8.5 starts → valet use php@8.5 done
→ status strip: php 8.5.x · 8.5 row now gold/global · sites moved to it
devkit tasks --limit=1 && devkit status | grep -E 'php|fpm'
done  valet use php@8.5 · php 8.5.x · php-fpm running 8.5
If the task ends failed with no output at the moment fpm restarted, it was killed with the old fpm's process group — posix_setsid() didn't take. /opt/homebrew/bin/php -m | grep posix must print posix. Everything else about the switch happened anyway (Valet did it); only devkit's record is wrong.
Your terminal's php changed too — that's what valet use means. Composer's global packages (Valet itself) keep working across 8.2–8.5.
8.4 row → use → yes → same sequence → 8.4 global again
Stuck with a dead dashboard after a switch (red "api unreachable", 500 on the page)? The global fpm is a version devkit can't run on. From a terminal: devkit use php@8.4. The switch task still completed — devkit tasks will show it done.

3Install a version optional · brew bottle, a minute or two~5 min

devkit php:install 8.1
brew install shivammathur/php/php@8.1 … brew's own output … php@8.1 installed. Use it per site: devkit isolate php@8.1 --site=<name> …
Or from the dashboard: the install picker under the table lists the same "installable" set and runs it as a task — check Tasks for the brew log. Either way the new row appears with no fpm until a site isolates to it.
curl -s -X POST -H 'X-Devkit: 1' -H 'Accept: application/json' -w '\n' http://devkit.test/api/php/8.3/use
{"message":"devkit's dashboard runs on the global PHP and its dependencies need 8.4+; isolate sites that need php@8.3 instead: devkit isolate php@8.3 --site=<name>"}   ← 422
8.3 rather than 8.1 because the guard order is: installed? → at or above devkit's floor? An uninstalled version answers "not installed" first. -w '\n' instead of ; echo: zsh's URL quoting turns a pasted ; into \;, which makes curl request /use; and then try to resolve a host named "echo". Accept: application/json keeps Laravel's errors JSON instead of the HTML 404 page.

4Updates ~3 min

brew update >/dev/null && devkit php:list --fresh
the update column shows a newer patch where one exists, "-" otherwise
devkit php:update
brew upgrade php@X.Y for each outdated one, streamed · "Every installed PHP is current" if none · then: devkit restart
Dashboard equivalent: "check updates" top-right re-runs the check; "update → 8.x.y" appears on the row and runs as a task. Restart fpm afterwards (devkit restart) so the updated binary serves.

5Commit and hand-off

git add -A && git commit -m "phase-1c: brew bridge, php manager, php:list|install|update, /api/php, php page"

Paste the pest summary and devkit php:list. 1d closes Phase 1: ini, db, edit, config:get|set — CLI only.

!Troubleshooting

php:list shows nothing installed — brew_prefix in ~/.devkit/config.json is wrong or missing; ls $(brew --prefix)/opt | grep php@ is what it reads. Re-run ./install/install.sh --skip-node to rewrite it.
installable list is only the installed versions — the tap isn't checked out locally (Homebrew 6's JSON API mode). brew tap shivammathur/php once; the Formula dir appears and the full list follows.
brew install / upgrade task fails — devkit task:log <id> has brew's message. "Refusing to load formula … untrusted tap" → brew trust shivammathur/php (runbook 0a).
After a switch the dashboard stays dead — the new global fpm isn't up. devkit status from the terminal; devkit restart starts it. If curl -sI http://devkit.test is 502, the fpm for the global version is the one missing.
