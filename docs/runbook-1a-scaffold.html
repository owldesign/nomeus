Apply slice zips with unzip -o … -d ~/Code/ — it overlays files and never deletes. Dragging folders in Finder and choosing "Replace" swaps out whole directories, which silently removes skeleton files (tests/TestCase.php, app/Http/Controllers/Controller.php, routes/console.php, …) that live next to ours. The installer checks for these and prints the restore command.
Order matters in this phase: our files go in first, then the Laravel skeleton is merged around them with --ignore-existing. That is what lets us ship a full bootstrap/app.php, routes/web.php and .env.example without hand-editing the skeleton's copies.

Any field that differs from 5.1 is php-fpm's stripped environment. Don't guess — diff the two diagnostics dumps: 
devkit status --diagnose > /tmp/cli.json; curl -s 'http://devkit.test/api/status?diagnose=1' > /tmp/fpm.json; diff <(python3 -m json.tool /tmp/cli.json) <(python3 -m json.tool /tmp/fpm.json)
env.PATH and commands.*.stderr in the fpm dump name the cause. composer_bin and brew_prefix in ~/.devkit/config.json are what fpm uses to build PATH — the installer writes them; if they're missing, re-run ./install/install.sh --skip-node.

!Troubleshooting

devkit.test → 502 Bad Gateway — php-fpm for the global version isn't up.
devkit restart && tail -20 ~/.config/valet/Log/nginx-error.log
devkit.test → Laravel error "Vite manifest not found" — assets never built.
npm run build
fpm diagnostics: "sudo: a terminal is required to read the password" — Valet 4.12 sudo's for every non-read command, and its NOPASSWD rule only matches /opt/homebrew/bin/valet. devkit now always invokes that path; the rule itself comes from:
devkit trust && sudo cat /etc/sudoers.d/valet
Expect Cmnd_Alias VALET = /opt/homebrew/bin/valet * and %admin … NOPASSWD. If diagnostics.groups in the fpm dump lacks admin:80, php-fpm's worker isn't in the admin group and the rule can't apply — say so, that's a different fix.
CLI and /api/status disagree (version null, fpm "unknown", a service "stopped" that curl proves is up) — always the fpm environment. devkit status --diagnose vs /api/status?diagnose=1, see 5.3. Valet's sockets in ~/.config/valet/*.sock are the fpm source of truth; pgrep is only the fallback.
Dashboard strip says "api unreachable" — open /api/status directly; a 500 there is a PHP exception, read storage/logs/laravel-*.log. A 403 means you're not on loopback (VPN with a non-loopback route to yourself?).
devkit: command not found — brew's bin dir isn't on PATH in this shell, or the symlink was skipped.
ls -l "$(brew --prefix)/bin/devkit" || ./install/install.sh --skip-node
tsc errors in Layout.tsx / Status.tsx — React types missing.
npm install -D @types/react @types/react-dom
pest: "Class Tests\TestCase not found" — a skeleton file is gone, almost always because a slice was applied by replacing folders. Re-run the 1.2 rsync (recreate /tmp/devkit-skel via 1.1 if /tmp was cleared); it restores only what's missing.
zsh: permission denied: devkit — the execute bit on bin/devkit was lost in transit.
chmod +x ~/Code/devkit/bin/devkit
The installer now restores it on re-run.
