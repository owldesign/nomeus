What you're proving: Xdebug per PHP version with three honest modes — off (not loaded), on (every request), trigger (only when asked) — switchable from the CLI or the Debug page, and a breakpoint in smoke that PhpStorm actually stops at. Precondition: 5a committed. PhpStorm with "Start Listening for PHP Debug Connections" available (the phone icon), port 9003 (its default).

1Install for 8.4 ~3 min

brew trust shivammathur/extensions · brew install shivammathur/extensions/xdebug@8.4 … · moved the formula's 20-xdebug.ini aside · php 8.4: xdebug /opt/homebrew/opt/xdebug@8.4/xdebug.so · mode off
20-xdebug.ini.devkit-off  99-devkit.ini  (plus whatever else was there)
exit 1   ← mode off: the extension is not loaded, php -m doesn't list it
The formula's own ini loads Xdebug on every request with no way to turn it off short of deleting the file; that's why it's moved aside rather than left in. brew upgrade may put it back — the doctor and the Debug page both flag that, and setting any mode re-quarantines it.

2on: a breakpoint that hits ~6 min

Settings → PHP → Debug:
  ☐ Force break at first line when no path mapping specified
  ☐ Force break at first line when a script is outside the project      ← default on: pauses every request in devkit's prepend.php
  Max. simultaneous connections: 10                                        ← default 1: everything queues behind one paused request
  ☑ Ignore external connections through unregistered server configurations
With mode "on" every PHP request connects — the dashboard's own polls included. One paused request plus a connection limit of 1 exhausts php-fpm and both devkit.test and your sites stop answering until you stop the session (Debug window → red square) and stop listening.
PhpStorm → open ~/Sites/smoke → click the listen icon top-right (a bug with a red ✕; hover says "Start Listening for PHP Debug Connections" — it turns green) → put a breakpoint on the `return` in routes/web.php's `/` route (click the gutter left of the line; a red dot appears)
first connection: "Incoming Connection From Xdebug" → Manually choose → smoke → OK (registers Valet's server name, "!valet!", once)
devkit xdebug:mode on && devkit xdebug
php 8.4: xdebug on · valet restart php · (no "nothing is listening" warning — PhpStorm is) · table: 8.4 installed on · IDE listening on 127.0.0.1:9003
curl -sk https://smoke.test/ -o /dev/null -w '%{http_code}\n'
curl waits… PhpStorm pops up on the breakpoint (first time: "Incoming connection from Xdebug" → accept, map the server path to the project) → resume → curl prints 200
"on" means every request from every site connects to 9003. Stop listening in PhpStorm and the same curl takes ~200 ms longer per request while Xdebug times out — that's the cost the mode names warn about, and why 2.3 exists.
devkit xdebug:mode trigger && curl -sk https://smoke.test/ -o /dev/null -w '%{http_code}\n' && curl -sk 'https://smoke.test/?XDEBUG_TRIGGER=1' -o /dev/null -w '%{http_code}\n'
(stop listening in PhpStorm before the mode switch, or the CLI run itself connects first; start listening again before the second curl)
php 8.4: xdebug trigger · valet restart php · first curl: 200 at once, no breakpoint · second curl: PhpStorm stops on the breakpoint → resume → 200
cd ~/Sites/smoke && XDEBUG_TRIGGER=1 php artisan about | head -3; cd -
the CLI form: PhpStorm stops on any breakpoint reached by artisan; without the env var, artisan runs untouched
For browsing, the "Xdebug helper" extension sets the same trigger as a cookie with one click — this is the everyday mode: loaded, quiet, ready.

!Troubleshooting

devkit.test and every site stop loading after switching on — PhpStorm paused a request (its "force break at first line … outside the project" default hits devkit's prepend.php) and its connection limit of 1 queued the rest; php-fpm has no workers left. Debug window → stop the session, stop listening, sites recover; then apply 2.0 before listening again.
brew: "No available formula … xdebug@8.4" — the tap doesn't build for that PHP yet (new minor); brew search shivammathur/extensions/xdebug lists what exists.
Breakpoint never hits with mode on — PhpStorm isn't listening (phone icon), or its port isn't 9003 (Settings → PHP → Debug → Xdebug port; or devkit config:set xdebug.port 9000 and set the mode again), or fpm didn't restart (valet restart php). curl -sk https://smoke.test/ taking ~200 ms extra with nothing listening is the sign Xdebug is active and trying.
Breakpoint hits in a vendor file / wrong file — PhpStorm path mapping: map the server root to the project root once (it asks on first connection).
php -m shows Xdebug with mode off — a second ini still loads it: php --ini, then look for another zend_extension line (a hand-written one in php.ini, or the tap's file back after an upgrade — devkit xdebug:mode off re-quarantines that one).
pest/composer got slow — mode on affects the CLI too (same ini). XDEBUG_MODE=off vendor/bin/pest for one run, or switch to trigger.
