2API header guard, then real mutations~5 min

curl -s http://devkit.test/api/sites | python3 -m json.tool | head -20; curl -s -o /dev/null -w '%{http_code}\n' -X POST http://devkit.test/api/sites/smoke/secure
JSON list matching 1.1 · then 403 — no X-Devkit header, no mutation
dk (defined in 2.2) is just curl with the two headers; zsh doesn't word-split variables, so a function beats a $FLAGS string. The header is the whole cross-origin defence: any page that isn't devkit.test would have to preflight to send it, and config/cors.php answers no preflight. A plain form post can't carry it at all.
dk() { curl -s -H 'X-Devkit: 1' -H 'Content-Type: application/json' "$@"; echo; }
dk -X POST http://devkit.test/api/sites/smoke/unsecure; sleep 4; devkit tasks --limit=1; devkit secured
{"task":{"id":"20260901-…","label":"valet unsecure smoke","status":"queued",…}}   ← 202, immediately
tasks: … done  valet unsecure smoke   ·   secured list without smoke
dk -X POST http://devkit.test/api/sites/smoke/secure; sleep 4; devkit tasks --limit=1; devkit secured
202 again · done · smoke back in the secured list
Mutations answer 202 with a task and finish in the background: valet secure restarts nginx, which would cut off any inline response — the "Failed to fetch" you saw in the browser before this change. devkit tasks and devkit task:log <id> are the audit trail; the dashboard's Tasks page shows the same.
A task that ends failed with sudo: a password is required in its log means the trust rule isn't in effect for php-fpm — devkit status must say trusted. If it does and this still fails, paste the message: that would be the group-membership case from 1a's diagnostics.
dk -X POST -d '{"php":"8.3"}' http://devkit.test/api/sites/smoke/isolate; sleep 10; devkit tasks --limit=1; echo '<?php echo PHP_VERSION;' > ~/Sites/smoke/public/v.php; curl -s https://smoke.test/v.php; echo; devkit status | grep php-fpm
202 · done  valet isolate php@8.3 --site=smoke · 8.3.x from the site · php-fpm running 8.3, 8.4 (both sockets answering)
dk -X POST http://devkit.test/api/sites/smoke/unisolate; sleep 5; curl -s https://smoke.test/v.php; echo; rm ~/Sites/smoke/public/v.php
202 · 8.4.x again
First isolation to a version installs its fpm config and starts it — expect a few seconds. Valet 4.12 leaves the 8.3 fpm running after unisolate; that's Valet's behaviour, not devkit's.

!Troubleshooting

422: "The [x] site could not be found in Valet's site list" — Valet's secure/isolate only accept parked or linked sites; proxies are managed with devkit proxy --secure. The dashboard hides actions on proxy rows for this reason.
Isolate succeeded but the site still serves the old version — browser cache or an fpm that hadn't finished starting. curl -s https://site.test/v.php with a phpinfo file is the honest check; devkit status must list the new version under php-fpm.
Task stays "running" for minutes — Valet is waiting on something interactive (keychain or sudo). devkit tasks shows it running; ps -ef | grep 'valet' shows what it's stuck on. Tasks time out (180 s secure/unsecure, 600 s isolate) and are then marked failed with whatever output exists.
Task dies as "failed" with no output right as nginx/fpm restarts — it was killed with the service's process group, meaning posix_setsid() didn't take. php -m | grep posix must list posix for the CLI php Valet linked.
Sites page is empty but devkit sites isn't — php-fpm reads a different ~/.config/valet: curl -s 'http://devkit.test/api/status?diagnose=1' and check env.HOME.
