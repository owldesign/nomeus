1Run it from the checkout ~6 min

swift run Nomeus
Compiles the app target (~30 s), then the four-point star from the logo appears in the menu bar, filled. No dock icon, no window. The terminal stays attached — ^C quits.
Unbundled means two things are off by design: notifications and launch-at-login both abort a process that has no .app around it, so AppSettings.isBundled gates them. Phase 2 turns them on.

Click the icon. Header: the star in lantern gold, "Nomeus · All services running · v2.1.0" (or "n services down"). Services: one row per instance with a coloured dot (green running, red stopped, orange crash-looping, grey formula missing), type/version/port, and restart/stop or start. Sites: every Valet site, lock icon when secured, open-in-browser and reveal-in-Finder (not for proxies). Footer: Dashboard, In browser, settings, quit.

Hover a dot: the tooltip is the launchd state ("Running, pid …" / "Loaded, not answering" / "Stopped"). That comes from /api/services, which is only fetched while the panel is open; the icon itself follows the cheap /api/status port probes.

Stop a service from the row. The row shows a spinner while the task runs (POST …/stop → 202 → polling /api/tasks/{id}), then the dot goes red and the menu bar star becomes an outline. Start it again; green, filled star. (All down: the star is struck through. API unreachable: faint outline.)

nomeus tasks --limit=3
The two lifecycle tasks the app enqueued, status done — same path as the dashboard's buttons.
If the row spins for a long time and then shows "… failed — see the Tasks page": that is the task's own non-zero exit, not the app. Open the dashboard's Tasks page for the log, exactly as you would after clicking the SPA button.
Seen on the first run: a 405 "GET method is not supported for route api/services/…/stop" that flashed and vanished. Cause: nomeus.test is secured, nginx 301s http → https, and URLSession follows a 301 by re-issuing the request as a GET (RFC behaviour). Reads survived that, every POST became a 405. Two fixes shipped: the transport no longer follows redirects — the model reads the Location, adopts that origin, retries the same method once and remembers it (Settings → Dashboard URL flips to https on its own) — and /api/status now says https://nomeus.test up front when the site is secured, so a fresh install never hits the redirect at all. curl -si http://nomeus.test/api/status | head -1 shows the 301 that was doing it.
Then a 403 "Missing X-Nomeus header." — RequireNomeusHeader (bootstrap/app.php, on every api route) demands X-Nomeus: 1 on any unsafe method; it's the CSRF / DNS-rebinding guard, and the SPA's client.ts sends it. The app now does too, on every POST, and the fake transport in the Swift tests enforces the same 403 so a new mutation path can't forget it. Reads never needed it, which is why the panel populated fine while every button failed.
Why both errors "quickly went away" — run() set the error, then the refresh it triggers cleared it, one poll later. The model now keeps two kinds apart: a refresh error clears itself on the next good refresh; an action error (failed task, 4xx/5xx on a button) stays until the next action or the ✕ on the line. The Swift test for the 422 case asserts the error survives a refreshAll(), which is the assertion that was failing.

Walked on macOS 26.5 / Xcode 26 (swift 6.3): 15 s for the universal build, and the zip is ~550K, not the ~3M guessed above — SwiftUI and WebKit are system frameworks, the binary is 1.8M and compresses well. codesign prints "replacing existing signature" first: SwiftPM already ad-hoc signs a release binary, the bundle signature replaces it. cp -R dist/Nomeus.app /Applications/ && open /Applications/Nomeus.app
Menu bar icon; same panel. First launch asks to allow notifications — allow, and answer it before you quit the app (below).
First bundled launch: the star came up faint and the panel said Nomeus is unreachable: The resource could not be loaded because the App Transport Security policy requires the use of a secure connection. Every poll had failed on the plain-http first request. Info.plist had NSAllowsArbitraryLoads and NSAllowsLocalNetworking — and macOS ignores the former the moment any narrower ATS key is present, while nomeus.test (dnsmasq → 127.0.0.1) doesn't count as "local". Phase 1 never saw it: swift run has no Info.plist, so ATS never applied. Fixed by dropping the second key; InfoPlistTests (test 30) reads Resources/Info.plist and fails if any of the narrower keys comes back.
The panel showed ports as :9,912. Text("… :\(service.port)") goes through LocalizedStringKey, which formats an Int with the locale's grouping separator. Now String(service.port).
The notification prompt is asked once. The app was killed while it was still on screen, and from then on macOS answered every requestAuthorization silently: no prompt, no callback, status denied — and Nomeus did not appear under System Settings → Notifications, so there was nothing to flip. What brought the prompt back, in this order: quit the app, delete every copy of Nomeus.app (/Applications and dist/), killall usernoted NotificationCenter, reinstall from the zip, launch. killall usernoted alone, a reinstall alone and launching a copy from another path did not. Settings now has a Notifications row (allowed / not allowed / not asked yet) read from notificationSettings(), so the state is visible without the log.
Settings (gear, or ⌘,) now enables the "Launch at login" toggle. Flip it on: macOS posts "Login Item Added — Nomeus will open automatically when you log in" and System Settings → General → Login Items lists Nomeus. That's SMAppService.mainApp — works with an ad-hoc signature because it registers the app itself, not a helper. Without opening System Settings: sfltool dumpbtm | grep -A6 'Name: Nomeus' shows Type: app · Disposition: [enabled, allowed, notified] · Bundle Identifier: dev.nomeus.app. The registration survives replacing the bundle in place.

Opens. That's the line in the README. Quit it (it's a second copy; the /Applications one is the real install).

Walked on macOS 26.5: the dialog is the "damaged" one, not "could not verify", and it offers only Move to Trash / Cancel — no right-click → Open, no "Open Anyway" in Privacy & Security. The app is also launched app-translocated (/private/var/folders/…/AppTranslocation/…/Nomeus.app) and killed. xattr -dr com.apple.quarantine is the only path on 26, which is why the README now says so; the process then runs from /tmp/Nomeus.app itself, same panel, "All services running".
Right-click → Open also works on macOS 14; on macOS 15 the first attempt is refused and System Settings → Privacy & Security → "Open Anyway" is the second. The xattr line is the same everywhere, which is why it's the documented path. A Developer ID + notarization removes the dialog entirely and changes nothing in this slice. Afterwards: quit the /tmp copy, delete it, and lsregister -f /Applications/Nomeus.app so LaunchServices points back at the real install (two registered copies with one bundle id confuse open and usernoted).

cd ~/Code/nomeus && git add -A && git commit -m "10a: Nomeus.app — SwiftPM menu bar shell over the API" && git push
Actions → macos: test (30 passed) → bundle → artifact "Nomeus.app" containing Nomeus-2.1.0.zip. ~5 min on a macos-15 runner, mostly the universal release build. ci (pest, 8.4 required / 8.5 reported) runs too — apps/macos/ isn't on its paths-ignore — and stays green: no PHP changed.
Two workflows, two jobs. macos.yml triggers on apps/macos/**, the favicon and config/nomeus.php — PHP-only pushes don't burn macOS minutes (10× the Linux rate on private repos; free on public). 4Troubleshooting as needed

swift build: "no such module 'SwiftUI'" — Command Line Tools SDK without the macOS 14 frameworks. Install Xcode, sudo xcode-select -s /Applications/Xcode.app, retry.
Icon appears but the panel is empty and the icon is the bolt — curl -s http://nomeus.test/api/status | head -c 200. HTML instead of JSON means nomeus isn't the linked site at that host (nomeus doctor); a hang means nginx/fpm (valet restart). If your dashboard is at another host, Settings → Dashboard URL.
Dashboard window is blank, white — WKWebView refused a mixed https/http situation. Set the Dashboard URL to exactly what nomeus status --json | jq .dashboard.url prints.
"Launch at login" greyed out — you're running swift run, or the .app is not in /Applications (SMAppService needs a stable path). Move it and relaunch.
No notifications ever — Settings → Notifications row. not allowed: the one-shot prompt was lost (the app quit while it was up, or Don't Allow); System Settings → Notifications → Nomeus if it's listed, else the reset in 2.2 (delete every copy, killall usernoted NotificationCenter, reinstall). available when running from Nomeus.app: you launched via swift run (gated). allowed and still nothing: nothing transitioned — notifications fire on running → stopped only.
"Nomeus is damaged and can't be opened" — macOS 26's wording for a quarantined app with no notarization; nothing is damaged. xattr -dr com.apple.quarantine /Applications/Nomeus.app, open again.
Panel says "App Transport Security policy requires the use of a secure connection" — an Info.plist with a narrower ATS key next to NSAllowsArbitraryLoads; swift test (InfoPlistTests) catches it before bundle.sh does.
log show prints nothing — you're in zsh and log is its builtin. /usr/bin/log show --last 5m --predicate 'process == "Nomeus"'.
codesign: "resource fork, Finder information, or similar detritus not allowed" — xattr -cr dist/Nomeus.app then rerun bundle.sh; happens when the icon was copied through Finder.
