4mysql ~5 min

grep -h 'MySQL Server - start\|starting as process' /opt/homebrew/var/mysql/*.err 2>/dev/null | tail -2; brew list --versions | grep mysql
the version that last ran the data (yours: 9.6.0) · the kegs brew has now (yours: mysql 26.7.0 after the upgrade)
MySQL's upgrade lineage is strict: an Innovation data dir may only move to the next release, and calendar-versioned 26.x may only be reached from the preceding LTS. 9.6 → 26.7 is refused ("Cannot upgrade from 90600 to 260700"); 9.6 → 9.7 LTS is allowed, and LTS is where site data belongs. Same rule for 8.4 data (8.4 → 9.7). Only 9.7 data can go to 26.7 — don't.

!Troubleshooting

"X's mysqld does not run: dyld: Library not loaded: …libprotobuf-lite.34…" — Homebrew dependency drift: a library was upgraded under a bottle that wasn't rebuilt. brew's own agent only ran because it loaded the old library before the upgrade; any fresh start fails. brew reinstall <formula>, then devkit services:start <name> if the instance was already created (its data copy is fine). The pre-flight now catches this before brew's service is stopped; services:doctor reports it as "binary <formula>".
adopt: "brew has no data directory for X" — brew's cluster lives somewhere non-default. cat ~/Library/LaunchAgents/homebrew.mxcl.X.plist shows the real -D/--datadir; the drivers assume brew's defaults (var/postgresql@N, var/mysql, var/db/redis).
mysql-error.log: "Invalid MySQL server upgrade: Cannot upgrade from 90600 to 260700" — see 4.1. The data needs mysql@9.7: devkit services:upgrade mysql mysql@9.7 --yes. The dyld lines above it in services:logs are older attempts from before brew upgrade; the newest lines are at the bottom of each log.
adopt: instance kept stopped, log says "database files are incompatible with server" — the formula devkit picked isn't the one that wrote the data (e.g. brew's postgresql bare formula vs postgresql@17). Delete the instance and adopt the exact formula name from devkit services:adopt's list.
ensure role postgres fails: "role owldesign does not exist" — brew's cluster superuser isn't your current username (created under another account). Connect as whatever role exists and CREATE ROLE postgres SUPERUSER LOGIN by hand; the instance itself is fine.
Sites can't connect after adopting mysql: "Access denied for user root" — the cluster had a root password; devkit didn't change it. Use it in the sites' .env as before; services:env's empty DB_PASSWORD is the convention for instances devkit initialized, not adopted ones.
Undo — devkit services:stop <name> && brew services start <formula>. brew's data was never touched.
